## Summary

This subsystem turns raw per-marketplace card lists into the ranked, explained search payload. Entry is aggregateMarketplaceResults (src/aggregate.js:1031), called by app.js:396/418 (searchAcrossSites, mock and live), worker.js:921 and server.js:323 (premium merge), and shop-validation.js:61. Per source it normalizes each card (normalizeListing, src/normalize.js:144: price text -> numericPrice/currency/priceRon with a fixed EUR=5 RON rate, image and phone extraction), tags marketType via classifyMarketSegment (src/market-segment.js:18: sourceType/sellerType -> retail|secondary|mixed), then classifies each listing against the query with classifyListingIntent (src/relevance.js:1449). That classifier builds a query profile (tokens, brand aliases, QUERY_ALIASES categories, hand-curated PRODUCT_TAXONOMY, understandMarketplaceQuery entity/family/vehicle-make, queryType wanted/service/spare_part/accessory/main_product), finds negative matches (NEGATIVE_INTENTS word lists, NEGATIVE_PHRASES, CATEGORY_EXCLUSIONS, vehicle-evidence gate, per-category RON price floors, multi-model catalog detection), computes match stats and critical-token/model/variant/storage mismatches, derives a listingType (getListingType, relevance.js:1236) and a 0-100 relevanceScore, and emits rejectionReasons plus isRecommendedCandidate (hard rejections: missing_brand, type_mismatch, variant_mismatch, wanted/service/broken/commercial; thresholds typeCompatibility>=0.8, score>=55, no missing critical tokens). aggregate.js applies the condition filter (matchesCondition, aggregate.js:79), splits items into productMatches vs relatedAccessories/partsAndRepair/wantedAds/secondaryMatches (only productMatches survive as result.items), computes a per-source median and offerScore (scoreOffer, aggregate.js:585), then dedupes across sources (retail by normalized title, used by exact URL; survivor by offerScore->price->image->identity). Global stage: used/new/global medians, a comparable cohort per item (comparableKey from query understanding; vehicles need same entity and <=4-year gap, else the pool is the item itself), deal intelligence enrichment (priceInsight, riskFlags, phoneSpecs, evidenceConfidence, dealQuality, whyThisDeal), recommendationScore (scoreGlobalRecommendation, aggregate.js:670), and a deterministic sort by semantic tier (relevance>=90/75) then recommendationScore then price then listing identity. Post-rank, items in pools <2 are capped at 79, priceInsight is downgraded to 'esantion insuficient', and a recommendation explanation with strong/summary/reasons/cautions is attached. The summary exposes stage counts (parsed/matched/queryMismatch/included/excluded/duplicate), bestOffer, bestUsedOffer (first non-retail, which includes 'mixed'), closestUsedOffer (proximity from src/location-intelligence.js city-center haversine, never affecting score), bestNewBenchmark (cheapest retail), recommendedOffers (best per site, top 4), priceIntelligence (used/new medians, fair ranges, savingsVsNewPct, comparable=false withholding for vehicles without >=2 comparables) and recommendationMode deal|match. src/location-intelligence.js also resolves viewer location from request.cf / cf-* headers / near= / LIBERGENT_DEMO_CITY and produces the coarse cache key used by worker.js:125. src/schema.js only feeds the Cloudflare/Firecrawl AI-extraction providers (search.js:295-345), not the default direct-HTML path. Documented behavior in README.md:85-137 matches the code structurally, but two README claims are not fully true: cross-source dedupe of used listings (README:24) does not happen, and the coarse-location cache key (README:121) collides for viewers in unrecognized cities. Empirical probes (offline node runs against the modules) confirmed several gating bugs that hit the tech-first direction: the vehicle-make list in query-understanding.js turns 'iphone 13 mini', 'ipad mini', 'mac mini', 'smart tv', 'nintendo ds' into vehicle queries with a 7000 RON floor (all listings rejected), and generic 'part' tokens (usa, display, baterie, motor) or exclusions (sim, controller, jocuri) flip complete products into spare_part with a hard rejection.

## Notable design decisions

- Three-stage funnel with auditable counts: search.js filterRelevantItems (token coverage >=50%, mandatory numeric tokens) -> matchedListings; relevance.js classification -> excludedListings (only isRecommendedCandidate items remain in result.items, aggregate.js:1057); dedupe -> duplicateListings (aggregate.js:863-910). Matches README.md:85-97.
- Fully deterministic, rule-based ranking with no ML; final tie-breaker is a stable listing identity (compareListingIdentity, aggregate.js:574-578), tested for order-invariance (aggregate.test.js:15-34). README.md:181.
- Semantic tier before deal quality: semanticMatchTier (relevance >=90 -> 3, >=75 -> 2) sorts ahead of recommendationScore (aggregate.js:956-961, :1130-1133), so a cheap weak match cannot outrank an exact one (README.md:110).
- Comparable-cohort price claims: comparableKey from query-understanding; vehicles require same entity and <=4-year gap (aggregate.js:925-942) else pool = self; vehicle priceIntelligence is withheld (comparable:false) when the best used offer has <2 comparables (aggregate.js:1233-1246). Non-vehicle items use segment medians over all product matches.
- Used vs retail separation via classifyMarketSegment; separate used/new medians; per-item reference median chosen by segment (aggregate.js:912-917); bestNewBenchmark = cheapest retail item (aggregate.js:1212-1214); savingsVsNewPct = best used vs cheapest new.
- Recommendation confidence gating: 'strong' requires rank 1 in pool, pool >=2, evidenceConfidence >=55, productMatch >=80, no 'bad' risk flag (aggregate.js:800-807); recommendationMode deal|match drives UI label Best Used Deal vs Top Match (aggregate.js:1256; README.md:115). Thin pools cap recommendationScore/dealQuality at 79 (aggregate.js:1149-1158).
- Dedupe policy: retail/new items by normalized title with brand/marketing words stripped (aggregate.js:23-29, :41-43); used items by exact URL only (aggregate.js:855-861); survivor chosen by offerScore -> lower price -> has image -> identity (aggregate.js:53-77).
- Title evidence beats description for phone model/storage/variant (relevance.js:1097-1100, :1117-1136) so 'upgrade la iPhone 15' in a description cannot rescue an iPhone 14.
- Hard rejections vs soft penalties: missing_brand, type_mismatch, variant_mismatch, wanted/service/broken/commercial are hard (relevance.js:1531-1539); per-category RON price floors (relevance.js:681-691) and vehicle-evidence gate (relevance.js:969-988) add 'irrelevant' negatives that flip listingType.
- Proximity is orthogonal to ranking: closestUsedOffer is chosen only among used offers with recommendationScore >=55 in the strongest semantic tier (aggregate.js:1198-1211); viewer coordinates are replaced by city centers or rounded to 0.1 degree and stripped from the public payload (location-intelligence.js:80-105, :108-117). README.md:119-121.
- Product knowledge is data, not code: PRODUCT_TAXONOMY (relevance.js:374-460), BRAND_ALIASES (462-516), QUERY_ALIASES (536-602), CATEGORY_EXCLUSIONS (604-679), PRODUCT_ENTITIES/FAMILIES in query-understanding.js:33-98 — but each is hand-curated and grown from individual test cases.
