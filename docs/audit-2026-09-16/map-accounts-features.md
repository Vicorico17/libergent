# Subsystem map: Alerts, feedback, conversations/outreach, leads, saved searches, history/trends, listing details, phone numbers, and the Supabase schema

Generated 2026-09-16 by a read-only code-reading agent. Evidence is `path:line` on commit 81c8e23. Claims were not independently re-verified unless noted in the [summary](../audit-2026-09-16.md).

## Summary

This area is the persistence and "account features" layer around the core search. All durable state lives in Supabase and is reached only through src/supabase.js, a thin PostgREST client that uses the service-role/secret key (SUPABASE_SECRET_KEY or SUPABASE_SERVICE_ROLE_KEY) and never the user's JWT; user scoping is done in code by adding user_id / raw->>userId filters, and the SQL enables RLS with no policies on the user-data tables so anon/authenticated roles are denied (search_tracking.sql:194-201, whatsapp_messages.sql:24-26). Pure modules do validation/normalization and business logic: alerts.js (profile normalization, vehicle-fact extraction, matching, event generation), feedback.js (structured like/dislike payload), conversations.js (grouping whatsapp_messages rows into per-seller-per-listing threads with inferred status), leads.js and saved-searches.js (email payloads), history-base.js (search-history entry and trends aggregation), listing-details.js (JSON-LD/og: parsing of a listing page), phone-numbers.js (Romanian E.164 extraction), and outreach.js + call-pipeline.js (consent-gated call/WhatsApp brief builders that are not wired to any route). The Cloudflare Worker (src/worker.js) exposes the HTTP routes and owns the Premium alert runner: the hourly cron (wrangler.toml crons "15 * * * *") calls runDuePremiumAlerts, which lists up to 20 due alert_profiles, re-checks the entitlement, runs a direct search restricted to autovit.ro + bestauto.ro, diffs against alert_listing_state, inserts deduplicated alert_events (unique event_key), records notification_deliveries after posting to an optional vendor-neutral email webhook, and reschedules next_check_at (24h for daily, 1h for "immediate"). The first scan of a profile only stores baseline state and emits no events. Premium access for both alerts and Premium search comes from readPremiumEntitlement (user_entitlements row, LIBERGENT_PREMIUM_EMAILS allowlist, or an undocumented LIBERGENT_PREMIUM_ALERTS_BETA=1 global bypass). Feedback is authenticated and written to offer_feedback with learning context, with a legacy fallback that writes into search_events through the log_search_event RPC if the feedback schema is stale. Seller messaging goes /api/whatsapp/send -> OpenClaw bridge (OPENCLAW_BRIDGE_URL/TOKEN) and stores an outbound whatsapp_messages row with raw.userId/listing; inbound replies arrive at /api/openclaw/inbound (bearer OPENCLAW_INBOUND_TOKEN) and are attributed to an owner only when exactly one account previously messaged that seller phone, otherwise they stay unassigned. Search history is logged from every search (including cache hits) via the log_search_event RPC, which also increments search_query_stats/keyword_stats; /api/history (public trends page) reads those tables with six Supabase requests per hit, and the Node dev server additionally keeps a local data/search-history.json fallback. Listing enrichment (/api/marketplace/details) and contact lookup (/api/marketplace/contact) fetch supported marketplace pages server-side, parse them with listing-details.js / phone-numbers.js (plus OLX phone endpoints and an optional Browser Rendering reveal), and cache results in the Cloudflare cache. Email leads and saved searches are unauthenticated upserts; saved_searches has no consumer and the UI never calls it. The Node server (src/server.js) mirrors only alerts CRUD, feedback, leads, saved-searches and history, so conversations, WhatsApp, inbound, listing details/contact, price history and the alert runner exist only in the Worker. Every table referenced by src/supabase.js exists in supabase/*.sql with matching columns and on_conflict targets; the notable schema gaps are missing RLS/grant revocation on the four search-analytics tables and no execute-revocation on the SECURITY DEFINER RPC.

## Notable design decisions

- All Supabase access is server-side with the secret/service-role key; RLS is enabled with zero policies on user-data tables so anon/authenticated are denied and ownership is enforced in code via user_id / raw->>userId filters (supabase.js:423,452,472,480,609; search_tracking.sql:194-201; whatsapp_messages.sql:22-26)
- Premium gating is one function (readPremiumEntitlement) shared by Premium search and alerts, with an email allowlist for beta testers before billing exists (supabase.js:403-418; README.md:409)
- Alerts are vehicle-only by design: criteria are car fields (year/mileage), facts are regex-extracted from title/condition, and scans query only autovit.ro + bestauto.ro (alerts.js:42-48; worker.js:504; docs/premium-alerts-todo.md:141)
- First scan is a silent baseline (eventsToInsert = [] until last_checked_at is set), events are deduplicated by a unique event_key with ignore-duplicates upsert, and only newly inserted events are delivered (worker.js:510-522; supabase.js:516-522)
- Every scan re-checks the entitlement and pauses the profile with last_error when Premium lapses (worker.js:496-501)
- Frequency 'immediate' means hourly (next_check_at +1h) and gets per-event emails; 'daily' gets a digest (worker.js:514-522; supabase.js:534)
- Inbound WhatsApp ownership is heuristic and fails closed: attributed only if exactly one account has outbound messages to that seller phone; ambiguous replies stay unassigned and invisible to everyone (supabase.js:616-626; README.md:458)
- Conversations are keyed by seller phone + listing URL; inbound rows without listing metadata attach to an existing thread for that phone (conversations.js:23-29,76-103)
- Delivery status requires provider evidence; a successful bridge HTTP response without a receipt is 'queued', nested result.ok=false is a failure and is not stored (conversations.js:31-37; worker.js:1256-1259)
- Search analytics aggregation happens inside Postgres via the SECURITY DEFINER log_search_event RPC that also increments query/keyword stats (search_tracking.sql:253-325); search events are logged for cache hits too (worker.js:828)
- Feedback is stored with rich learning context but has only a session-local ranking effect; a compatibility fallback writes feedback into search_events when the offer_feedback schema is stale (supabase.js:216-295; README.md:391-393)
- Listing details prefer JSON-LD Product/Offer, fall back to og: meta, and add Vinted-specific regexes for seller reputation and buyer-protection totals; results are cached 30 minutes and capped at 6 MB HTML (listing-details.js:174-221; worker.js:33-34,1309-1357)
- Phone handling is Romania-only E.164 and WhatsApp targets must be mobile (+407...) (phone-numbers.js:11-35; worker.js:1235)
- Outreach/calling is provider-neutral scaffolding with explicit consent + approval assertions and no dialing code; it is intentionally unwired (outreach.js:90-93; call-pipeline.js:9-12; .env.example:33-35)
- Table names are configurable via env with a public. prefix stripped because PostgREST wants unqualified names (supabase.js:28-31; README.md:420)
- SQL files are idempotent paste-in scripts (create if not exists / add column if not exists) rather than versioned migrations (search_tracking.sql:4-5,72-83)

## Risks and smells

- **high** `supabase/search_tracking.sql:194` — RLS is enabled only for email_leads, offer_feedback, saved_searches, user_entitlements and alert_* tables; search_events, search_query_stats, keyword_stats and vehicle_price_observations have no RLS and no 'revoke ... from anon, authenticated' (compare 332-341). Under Supabase default privileges these tables are readable/writable/deletable with the publishable key shipped in the UI bundle (NEXT_PUBLIC_SUPABASE_PUBLISHABLE_KEY). search_events.best_offer can also contain userId when the feedback fallback is used (supabase.js:277). Not verified against the live project.
- **high** `supabase/search_tracking.sql:347` — public.log_search_event is SECURITY DEFINER (253-268) and execute is granted to service_role but never revoked from PUBLIC/anon/authenticated (Postgres default grants EXECUTE to PUBLIC). With the publishable key anyone can POST rest/v1/rpc/log_search_event to inject arbitrary search events and inflate search_query_stats/keyword_stats, which feed the public trends page (/api/history). Not verified against the live project.
- **high** `src/supabase.js:357` — insertVehiclePriceObservations filters with Number(listing.price ?? listing.priceRon ?? listing.numericPrice); normalizeListing always sets price to the textual label (normalize.js:159), so Number('27 500 EUR') is NaN and every real listing is dropped (verified locally: returns false, no request sent). Vehicle price history is therefore never recorded and /api/vehicle/price-history (worker.js:1298) always returns null; daysOnMarket/price-change UI never gets data.
- **high** `src/worker.js:1217` — /api/whatsapp/send lets any authenticated account send arbitrary free text (up to 2000 chars) to any Romanian mobile number with no rate limit, per-user quota, opt-in template, STOP/opt-out handling or consent record. The compliance-oriented opt-in message and consent gates in outreach.js/call-pipeline.js are not used by this route. This is a spam/abuse vector and risks the OpenClaw WhatsApp number being banned.
- **medium** `src/phone-numbers.js:42` — Extraction regex (?:\+40|0040|0)\s*[2-7](?:[\s().-]*\d){8,9} is greedy and allows whitespace separators, so a phone followed by a space and a digit swallows that digit, normalization then fails and the phone is lost. Verified: extractRomanianPhones('Tel 0722 123 456 2019 km') -> [] and '+40 722 123 456 7' -> []. Affects normalize.js phones for every listing, call-pipeline job creation and the HTML fallback in /api/marketplace/contact.
- **medium** `src/worker.js:528` — On any failure inside runAlertProfile the catch calls completeAlertProfileCheck, which sets last_checked_at even though no baseline state was stored. The next run sees last_checked_at truthy (line 510) with an empty state map and emits new_strong_match/better_than_shortlist events (and emails) for the entire pre-existing inventory, breaking the documented 'first scan creates its baseline without notifying' guarantee (README.md:418).
- **medium** `src/supabase.js:406` — LIBERGENT_PREMIUM_ALERTS_BETA === '1' returns an active Premium entitlement for every authenticated user (Premium search and alerts). The flag is not documented in README or .env.example, so a stray var in Cloudflare would silently open Premium globally.
- **medium** `src/supabase.js:258` — When the offer_feedback insert fails with a schema-cache/table error, feedback is written through rpc/log_search_event as a fake search with query 'feedback:<query>' and provider 'feedback'. That RPC increments search_query_stats and keyword_stats, so feedback pollutes the public trends page and totals; it also copies userId into search_events.best_offer, a table without RLS.
- **medium** `src/worker.js:1150` — /api/history is public, unauthenticated and uncached; each hit performs six Supabase requests including three Prefer: count=exact HEAD counts (supabase.js:702-708) and returns the 100 most recent raw user queries with best-offer titles/URLs (supabase.js:733). Raw queries may contain personal data and the endpoint is an easy amplification target.
- **medium** `src/supabase.js:711` — readSupabaseHistoryPayload derives dailyTrend only from the most recent MAX_HISTORY_ENTRIES (500) search events, so on busy periods older days are undercounted or missing while totals.searches uses an exact count; the trends chart is inconsistent with its own totals.
- **medium** `src/worker.js:1168` — Unauthenticated email capture upserts any syntactically valid address into email_leads with consented_at defaulting to now() (search_tracking.sql:90) without verification, double opt-in or rate limiting; anyone can enroll third-party addresses and overwrite source/query/page_path for existing leads.
